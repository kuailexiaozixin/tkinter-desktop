# 01 需求澄清

> 目标：在写任何代码前，把"模糊想法"变成"可测试的验收标准"。

## 必问问题（首轮话术）

1. **做什么**：一句话说清工具的核心动作（"管理研发费用并出报表"、"批量重命名照片"）
2. **输入输出**：数据从哪来（手工录入 / Excel 导入 / 扫描目录）？结果到哪去（界面展示 / 导出文件 / 写数据库）？
3. **给谁用**：自己用（能接受简陋）还是给同事/客户用（要求防呆、美观）？
4. **数据量级**：几十条（怎么写都行）还是十万条（Treeview 要分页、查询要索引）？
5. **单机还是共享**：单机 SQLite 即可；多人共享要提前说明 Tkinter + 文件型数据库的并发局限
6. **交付形态**：源码脚本 / 单文件 EXE？EXE 是否需要图标、是否允许控制台窗口？

## 场景判断：该不该用 Tkinter

| 场景 | 判断 |
| ---- | ---- |
| 单机工具、表单+表格+报表、离线使用 | **Tkinter 最佳区间** |
| 需要复杂图表、Web 风格 UI、富文本 | 提示 Tkinter 在复杂图表/富文本上的局限，确认用户接受 ttk 朴素风格，或用 `tk.Canvas` 自绘、按需引入第三方图表库 |
| 需要触屏/动画/现代设计语言 | 提示 Tkinter 视觉上限，确认用户接受 ttk 朴素风格 |
| 无 GUI 需求（定时批处理） | 建议 CLI，不要强上 GUI |

## 产出：需求优先级表（MoSCoW）

| 优先级 | 含义 | 例子 |
| ------ | ---- | ---- |
| Must | MVP 必须有 | 项目 CRUD、费用录入、辅助账报表 |
| Should | 重要但可后置 | 报表导出 CSV、搜索过滤 |
| Could | 有更好 | 主题换肤、快捷键 |
| Won't | 本期不做 | 多人协同、云同步 |

同时为每条 Must 写一条可测试验收标准，格式：
`给定 <前置状态>，当 <操作>，则 <可断言的结果>`。
这些标准直接转化为 pytest 用例与冒烟检查项。

## 零基础用户沟通规范

- 不说"路由/控件/线程"，说"页面/按钮/后台处理"
- 每个阶段结束用一句话汇报："界面骨架已经能弹出来了，下一步接数据"
- 演示优先：能截图/能跑就先给用户看，不要长篇大论解释技术
